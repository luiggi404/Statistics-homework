HW3 — Two ciphers and the statistics of breaking them

A toy elliptic-curve scheme (built on the curve from HW1) and the Caesar cipher, encrypting the same message, then attacked: letter statistics against Caesar, and an exhaustive search against a deliberately small EC key space.

What this page is about. Two encryption schemes could not look more different — one is 2000 years old and shifts the alphabet, the other multiplies points on an elliptic curve — yet both are broken here, instantly, because their key spaces are tiny. The homework is really about how they break: the Caesar cipher falls to the statistical fingerprint of a language, the toy EC scheme falls to brute force over a restricted range. The last section explains why neither attack threatens a properly sized system.

1. Toy elliptic-curve encryption

Definition. Public-key (asymmetric) encryption uses a public key to encrypt and a different, secret private key to decrypt. Here the keys are points and scalars on the small curve y² = x³ + 7 (mod p) from HW1. Because inverting "multiply the base point by the private key" is hard in general, only the holder of the private key can read the message — unless, as in this homework, the key is drawn from a tiny range.

Parameters and keys

The scheme (a toy EC-ElGamal / ECIES):

  1. Keys. Private key d is a secret scalar in [1, n−1]. Public key is the point Q = d·G.
  2. Encrypt one character m (with the public key Q): pick a fresh random ephemeral scalar r, send C₁ = r·G, and compute the shared point S = r·Q. Mask the character with the x-coordinate of S: C₂ = m ⊕ (S.x mod 256). Ciphertext = (C₁, C₂).
  3. Decrypt (with the private key d): recover the same point S = d·C₁ = d·(r·G) = r·(d·G) = r·Q, so the mask S.x mod 256 is the same, and m = C₂ ⊕ mask.

The private key's role is to make S computable from C₁: it is the only secret, and everything else (p, G, Q, C₁) is public. Security rests on the attacker not being able to find d from Q = d·G (the elliptic-curve discrete-log problem) nor S from C₁ and Q (the Diffie–Hellman problem).

2. The Caesar cipher

Definition. The Caesar cipher is a symmetric monoalphabetic substitution: every letter is shifted forward by a fixed number k (the key, 0–25), wrapping around Z→A. The same k decrypts by shifting back. It is symmetric — one key both encrypts and decrypts — and the key space has only 26 values (25 useful ones).

4.4 Effectiveness and limitations

  • Single letters work from ~20 characters. By 30–50 letters unigram χ² and log-likelihood are essentially perfect: a short sentence is enough.
  • Bigrams win on very short texts. With 5–15 letters, scoring letter pairs (TH, HE, IN…) beats single letters, because word-boundary structure survives even when the single-letter counts are too noisy. By 20+ letters all methods converge.
  • The limitation is short or atypical text. On a 5-letter fragment even the best method is near 50 %, because several shifts can look plausible. Text that does not match the training language (names, code, another language, deliberately odd letter use like "jazz") also degrades the attack.
  • Exhaustive search is trivially possible too — only 25 keys — but it still needs a human or a language model to recognise the right plaintext. The statistical score is that recogniser, automated.

5. Attacking the restricted EC key space

The toy scheme is asymmetric and its ciphertext carries no usable statistics, so the Caesar approach is useless here. The weakness is elsewhere: the homework restricts the private key to a small range to keep experiments fast. That turns the discrete-log problem — normally the hard core of EC security — into a short search. Recover d from the public key Q = d·G, then decrypt.

5.3 Caesar attack vs EC attack

Statistical attack (Caesar)Key-search attack (toy EC)
What it exploitsStructure in the ciphertext — it preserves the language's letter statisticsSmallness of the key space — the ciphertext itself reveals nothing
NeedsA model of the plaintext language; enough ciphertext to be statistically significantOnly the public values (p, G, Q); no plaintext knowledge at all
Cost driverCiphertext length (signal), not key countKey-space size n (√n with BSGS)
FixDestroy the statistics (polyalphabetic ciphers, then modern encryption) — enlarging the 26-key space alone is not enoughEnlarge the key space to ~2²⁵⁶; the scheme is otherwise fine

Why the key-search attack fails on a real curve. A properly configured EC scheme draws d uniformly from ≈ 2²⁵⁶ values. Brute force would need ≈ 2²⁵⁶ operations and baby-step giant-step ≈ 2¹²⁸, both far beyond any computer that will ever exist (2¹²⁸ ≈ 3·10³⁸). There is no statistical shortcut like Caesar's: the mask is a hash-like function of a curve point and the ephemeral r re-randomises every character, so the ciphertext distribution is flat and carries no information about d. The toy scheme is broken only because the range of d was shrunk for the exercise — not because elliptic curves are weak.

5.4 Which weakness is which (optional)

  • From the restricted key space. The decisive one: a short d is found by brute force or BSGS. On a real curve this disappears.
  • From the toy design itself. Even with a large d, this toy would be weak for other reasons, and it is worth separating them: (i) the mask is only 8 bits (S.x mod 256), so each character has just 256 possible masks — a frequency attack on the masked bytes across a long message becomes possible, independent of the key; (ii) the group is tiny, so points repeat and the "hash" S.x is far from uniform; (iii) there is no integrity check, so ciphertext can be tampered with. Real ECIES fixes these with a proper KDF, a full-size symmetric cipher, and a MAC. These are design weaknesses, present even before the key space is restricted — a useful contrast with Caesar, whose weakness is entirely structural and cannot be patched by a bigger key.
