HW2 — From wallet seed to Ethereum address

Hashing, key derivation and the other cryptographic primitives behind every Ethereum wallet, with a live pipeline and some statistics.

What this page is about. A wallet such as MetaMask turns a list of 12 words into an address like 0xf39F…2266. That journey goes through six standards, and each one does a different kind of job: generating randomness, encoding it, deriving keys, public-key cryptography, hashing, and checksumming.

2. The standards and primitives

BIP-39 — mnemonic sentence and seed

Turns random bits into words a human can write down, and turns those words into a 512-bit seed.

The wallet draws 128–256 bits of entropy from a secure random generator. It appends the first ENT/32 bits of SHA-256(entropy) as a checksum (4 bits for 12 words), splits the result into 11-bit chunks, and maps each to one of 2048 words. The words are therefore just an encoding of the entropy plus a checksum. To get the seed, the sentence is fed to PBKDF2-HMAC-SHA512 with 2048 iterations and the salt "mnemonic" + optional passphrase. The iterations make brute-forcing phrases slower, and the passphrase acts as a "25th word".

BIP-32 — hierarchical deterministic (HD) derivation

From one seed, derives a whole tree of key pairs deterministically, so one backup covers every account.

HMAC-SHA512 of the seed gives the master private key and a chain code. Every child is again HMAC-SHA512(chain code, parent key ‖ index): the left half is added to the parent key (mod n), the right half becomes the child's chain code. Hardened children (index ≥ 2³¹, written with ′) use the parent private key as input. A leaked child key plus the parent xpub therefore cannot reveal the parent. Non-hardened children can be derived from the parent public key alone, which allows watch-only wallets.

BIP-44 — standard paths

Fixes the meaning of each level of the BIP-32 tree so that different wallets find the same keys.

m / purpose′ / coin_type′ / account′ / change / address_index, with purpose 44 and coin type 60 for Ether (registered in SLIP-44). Most Ethereum wallets use m/44′/60′/0′/0/i and create account i by incrementing the last index. Some, such as Ledger Live, increment the account level instead, which is why the same phrase can show different addresses in different apps.

secp256k1 — elliptic-curve public-key cryptography

The curve that links the private key to the public key and is used to sign transactions (ECDSA).

y² = x³ + 7 over a 256-bit prime field, defined by SECG (SEC 2, 2000) and adopted by Bitcoin and then Ethereum. The public key is Q = k·G, exactly the scalar multiplication of HW1, with a group of order ≈ 2²⁵⁶. Signatures prove ownership of k without revealing it, and Ethereum can even recover Q from a signature.

Keccak-256 — hashing

Compresses the 64-byte public key into a fixed-size digest; the last 20 bytes are the address.

Keccak is a sponge construction (1600-bit permutation). Ethereum uses it everywhere: addresses, transaction hashes, function selectors, storage slots. Hashing the key makes the address short (20 bytes instead of 64) and hides the public key until the account first signs something.

EIP-55 — mixed-case checksum

Adds error detection to an address without changing its length or its value.

Hex is case-insensitive, so the case of the letters a–f is free to carry information. EIP-55 hashes the lower-case hex text with Keccak-256 and upper-cases letter i when the i-th hex digit of that hash is ≥ 8. A wallet that receives a mixed-case address recomputes the pattern and rejects mismatches. All-lowercase addresses are still accepted, just without the check.

4. Trying it in real wallets

In MetaMask, Rabby, Rainbow or Exodus the "Secret Recovery Phrase" is the BIP-39 mnemonic. "Add account" walks the BIP-44 path by incrementing the last index (…/0/0, …/0/1, …). Importing the test phrase above into any of them on a test network shows the same first address 0xf39F…2266. Wallets also display or accept EIP-55 addresses and warn when the case pattern is wrong. Exporting a single account's "private key" gives the 32-byte key from the pipeline, but that key alone cannot regenerate the other accounts, because derivation only goes down the tree, never up.

5. Historical context

1977RSA: the first practical public-key cryptosystem (Rivest, Shamir, Adleman).
1985Elliptic-curve cryptography proposed independently by Koblitz and Miller.
2000SEC 2 publishes the curve secp256k1.
2001SHA-2 family (SHA-256, SHA-512) standardised by NIST.
2009Bitcoin launches, using secp256k1 and SHA-256.
2012BIP-32 hierarchical deterministic wallets. Keccak wins the NIST SHA-3 competition.
2013BIP-39 mnemonic code for deterministic keys.
2014BIP-44 multi-account hierarchy.
2015SHA-3 published as FIPS 202, based on Keccak. Ethereum mainnet launches, already committed to the original Keccak.
2016EIP-55 mixed-case checksum addresses.

The order tells a story. Public-key crypto (RSA, ECC) and standard hashes (SHA-2) came first as general tools. Bitcoin then needed a practical way to back up many keys, which led to BIP-32, BIP-39 and BIP-44. Ethereum reused all of that, chose Keccak while SHA-3 was still being finalised, and finally patched a usability gap (address typos) with EIP-55.

SHA-2 / SHA-512 vs Keccak / SHA-3 / Keccak-256

SHA-2 (SHA-256, SHA-512) uses the Merkle–Damgård construction: a compression function applied block by block. That construction is vulnerable to length-extension attacks, which is why HMAC is used for keyed hashing (as in BIP-32 and PBKDF2). Keccak is a completely different design, a sponge: a 1600-bit state is permuted while input is absorbed and output is squeezed. It is immune to length extension. NIST selected Keccak as SHA-3 but changed the padding during standardisation by adding domain-separation bits (padding byte 0x06 instead of Keccak's 0x01). Ethereum adopted the pre-standard Keccak. 6. Why several primitives instead of one?

Each step needs a property the others do not have, and no single algorithm offers them all:

  • BIP-39 / BIP-32 / BIP-44 → key management. Humans need one short, writable backup that can recreate unlimited keys in a standard place. This calls for an encoding with error detection (words + checksum), a slow KDF against guessing (PBKDF2), and a deterministic tree (HMAC-SHA512) with a standard map (paths).
  • secp256k1 → ownership. Others must be able to verify that you authorised a transaction without learning your secret. Only an asymmetric scheme with algebraic structure (Q = kG, ECDSA) can do that; a hash cannot sign.
  • Keccak-256 → identifiers. A compact, fixed-size, collision-resistant fingerprint of the public key. A hash must have no structure, which is the opposite of what signatures need.
  • EIP-55 → error detection. Catching typos cheaply and backward-compatibly is a usability problem, not a security one, so a simple checksum is enough.

Separating the roles also limits damage. If one primitive weakened, it could be swapped (for example a new derivation path or address format) without redesigning everything. Using one key for many purposes, by contrast, is a classic cause of cross-protocol attacks.

7. Statistical properties

The experiments below run in your browser on randomly generated test wallets.

7.1 BIP-39 checksum: how many random word lists are valid?

12 words carry 132 bits, of which 4 are checksum, so a random list of 12 words should be valid with probability 2⁻⁴ = 1/16 = 6.25 %. A single wrong word is detected with probability 15/16.

7.2 Avalanche along the pipeline

Take random entropy, flip one bit, and measure how much each stage changes.

7.3 Are addresses uniformly distributed?

Derive many addresses (m/44′/60′/0′/0/i, i = 0 … N−1) from a random phrase and test their hex digits and bits.

7.4 EIP-55: how strong is the checksum?

Only letters (a–f) can carry a check bit, and each hex digit is a letter with probability 6/16. The number of check bits in an address is therefore about Binomial(40, 3/8), with mean 15. A random wrong address passes with probability E[2−L] = (1 − 3/16)40 ≈ 0.0247 %.

7.5 Discussion

  • Entropy is the only source of unpredictability. Everything after it is deterministic, so the security of all keys equals the 128 (or 256) bits drawn at the start. Hashing and derivation can preserve randomness but never add any.
  • Encodings and checksums are not mixing functions. Flipping one entropy bit changes one word, plus sometimes the last word through the checksum. There is no avalanche there, and none is wanted. Avalanche appears as soon as a hash or KDF is applied: seed, keys and address each change in about 50 % of their bits.
  • Hash outputs are statistically uniform. Address digits and bits pass chi-square and balance tests, as expected from Keccak-256. The private key looks uniform too, because it is derived through HMAC-SHA512 and reduced mod n.
  • Uniformity is not security. These tests would also pass for a hash of a 20-bit secret. Security comes from the size of the input space (2¹²⁸ phrases), the slowness of PBKDF2, and the one-wayness of ECDLP and Keccak.
  • Collision probabilities. With 160-bit addresses, the birthday bound for some collision is about 2⁸⁰ addresses. Hitting a specific address needs about 2¹⁶⁰ tries. Both are far out of reach.
  • Checksums trade bits for error detection. BIP-39 spends 4–8 bits (1/16 to 1/256 false-accept rate). EIP-55 spends about 15 "free" bits of letter case (≈ 1/4000 false-accept rate) without changing the address.
